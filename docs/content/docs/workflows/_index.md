Forge.go ships reusable GitHub Actions pipelines that give every project the same checks, release process and delivery. `forgego init` generates a root workflow, `.github/workflows/.index.yml`, whose jobs each call one pipeline. This page covers the generated workflow, when each pipeline runs, and the permissions they need; the [pipeline reference]({{< relref "reference.md" >}}) describes each pipeline's stages and inputs.

## Names on the run page

A root job calls a pipeline, and a pipeline's jobs are its stages, so a run page lists every job as `<pipeline> / <stage>`: `service / lint`, `version / release`, `pages / deploy`. No pipeline calls another, so there's never a third level. A pipeline an event doesn't need, such as `publish` on a pull request, shows as one skipped row.

A root job's id is the pipeline's name. A second call to the same pipeline names its variant in brackets, such as `service (api)`.

## Pipelines

| Pipeline | Stages | Purpose |
| :--- | :--- | :--- |
| `library.yml` | lint, scan, test, test (windows), test (macos), build | A library's checks, with Windows and macOS when asked |
| `service.yml` | lint, scan, test, test (windows), test (macos), build | A backend's checks, with Windows and macOS when asked |
| `website.yml` | lint, scan, test, build, check | A Hugo website's checks, the build, and optional link and accessibility checks of it |
| `docker.yml` | build, push | A multi-platform image: built on pull requests, pushed to GHCR on a release |
| `version.yml` | release | release-please: the release pull request, then the tag and the draft GitHub release |
| `publish.yml` | package, assets (native), assets, attest | A library fetched through the Go module proxy; a service's binaries (and `.deb`) attached to the release by GoReleaser, or built natively, and their build provenance attested |
| `pages.yml` | deploy | The built website, to GitHub Pages |
| `patch.yml` | update | `task sync`, proposed through a pull request |
| `merge.yml` | review, squash | A review request on Dependabot's pull requests, and the squash merge of a minor or patch update once the checks pass |

The stages are `lint` (`forgego sync --check`, `go mod tidy -diff` and golangci-lint), `scan` (Gitleaks, OSV-Scanner and govulncheck), `test`, `build`, `check` (a check of a built result), `push`, `release`, `package`, `assets`, `attest`, `deploy`, `update`, `review` and `squash`.

There is no separate packaging pipeline: a `--debian` project uses `service.yml`, and GoReleaser builds the `.deb` in `publish.yml`'s `assets` stage.

## When each pipeline runs

| Event | Pipelines |
| :--- | :--- |
| Pull request | The checks (`library`, `service` or `website`, then the `docker` build), then `merge` on Dependabot's |
| Push to `main` | `version`; on a release, the checks again, then `publish`, `pages` or the `docker` push |
| Manual run, `auto-merged` dispatch | The same as a push to `main`, and `patch` |
| Weekly schedule | `patch` |

A project without versioning has no release to wait for: its checks run on every push to `main` as well, and a website deploys from every push.

## Generated workflow

`forgego init` writes `.github/workflows/.index.yml` for the selected mode. Every one starts with the same triggers and concurrency rule: a newer push to a pull request cancels the run it replaces, and every other run has a concurrency group of its own, so a run on `main`, running or queued, is never cancelled and a release is never created without being published.

```yaml
name: index

on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]
  workflow_dispatch:
  repository_dispatch:
    types: [auto-merged]
  schedule:
    - cron: '17 3 * * 1'

concurrency:
  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: true
```

**Library**, generated by `forgego init --library`:

```yaml
jobs:
  version:
    if: ${{ github.event_name != 'pull_request' && github.event_name != 'schedule' }}
    uses: apollogeddon/forgego/.github/workflows/version.yml@main
    with:
      app_client_id: ${{ vars.RELEASE_APP_CLIENT_ID }}
    secrets:
      APP_PRIVATE_KEY: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}
    permissions:
      contents: write
      pull-requests: write

  library:
    needs: version
    if: ${{ !cancelled() && (github.event_name == 'pull_request' || needs.version.outputs.new_release_published == 'true') }}
    uses: apollogeddon/forgego/.github/workflows/library.yml@main
    permissions:
      contents: read
      pull-requests: write

  publish:
    needs: [version, library]
    if: ${{ !cancelled() && needs.library.result == 'success' && needs.version.outputs.new_release_published == 'true' }}
    uses: apollogeddon/forgego/.github/workflows/publish.yml@main
    with:
      tag_name: ${{ needs.version.outputs.tag_name }}
      package: true
      assets: false
    permissions:
      contents: read

  patch:
    if: ${{ github.event_name == 'schedule' || github.event_name == 'workflow_dispatch' || github.event_name == 'repository_dispatch' }}
    uses: apollogeddon/forgego/.github/workflows/patch.yml@main
    permissions:
      contents: write
      pull-requests: write

  merge:
    needs: library
    if: ${{ !cancelled() && github.event_name == 'pull_request' && github.event.pull_request.user.login == 'dependabot[bot]' }}
    uses: apollogeddon/forgego/.github/workflows/merge.yml@main
    with:
      checks_passed: ${{ !contains(needs.*.result, 'failure') && !contains(needs.*.result, 'cancelled') }}
    permissions:
      contents: write
      pull-requests: write
```

The other modes differ only in their jobs:

| Mode | Jobs |
| :--- | :--- |
| `--backend` | `version`, `service`, `publish` (GoReleaser, with `contents: write`, and attestations from a public repository), `patch`, `merge` |
| `--library` | `version`, `library`, `publish` (the Go module proxy), `patch`, `merge` |
| `--website` | `version`, `website`, `pages` (from a public repository), `patch`, `merge` |
| `--debian` | As `--backend`: GoReleaser builds the `.deb` from the `nfpms` section of `.goreleaser.yaml` |

- `--docker` adds a `docker` job after the checks: it builds on pull requests, and builds and pushes on a release. `merge` waits for it, so a broken image stops a Dependabot merge.
- `--no-testing` passes `run_tests: false` and `--no-linting` passes `lint: false` to a backend's or library's checks, which skips their `test` stage and golangci-lint.
- `--no-versioning` leaves out `version` and `publish`: the checks, and a website's deploy, run on every push to `main` instead.

The workflow names no Go version: CI reads it from `go.mod`, which `init` writes with the `--go` version.

### An existing `index.yml`

If `.github/workflows/index.yml` calls Forge.go's pipelines, `init` removes it once it has written `.index.yml`, so the same checks don't run twice. It removes the file only when it's exactly as `init` generated it, ignoring line endings, trailing spaces, blank lines and a `go_version` copied from `go.mod`. One you've changed, say to set `runs_on`, is kept with a warning until you run `init --force`: move your changes to `.index.yml` first. A workflow that calls none of Forge.go's pipelines is your own and is never removed; check it doesn't repeat `.index.yml`'s jobs. Nothing is removed when `init` kept an existing `.index.yml`.

`forgego sync` never touches `.index.yml`: like the other generated configs, it's yours once written.

## Secrets

No secrets need passing. The pipelines only use the `GITHUB_TOKEN` that every called workflow receives, unless you set up a [release app](#release-pull-requests-that-run-the-checks), so don't add `secrets: inherit`: it would hand every repository secret to a workflow in another repository. A library is published by its Git tag, so it needs no registry credentials either. `publish.yml` takes two optional secrets for [signed releases]({{< relref "reference.md#signed-releases" >}}), and `version.yml` one for the release app; pass them by name.

GitHub doesn't start workflow runs for events made with `GITHUB_TOKEN`. So release-please's release pull requests don't run your checks on their own (they wait for a push to the branch, or a [release app](#release-pull-requests-that-run-the-checks)), and the push a Dependabot merge makes to `main` doesn't run the pipeline either. The `merge` pipeline therefore sends a `repository_dispatch` event, `auto-merged`, once the pull request has merged: one of the two events `GITHUB_TOKEN` may start a run with. `.index.yml` listens for it, so `main` runs `version` and release-please opens or updates its release pull request, and `patch` proposes the files a Forge.go update refreshes. The event runs on the default branch. The pull request `patch` opens is made with `GITHUB_TOKEN` too, so close and reopen it to run its checks.

### Release pull requests that run the checks

A pull request release-please opens with a GitHub App's token runs the checks like any other. The generated `version` job passes the app's client ID from the `RELEASE_APP_CLIENT_ID` repository variable and its private key from the `RELEASE_APP_PRIVATE_KEY` secret; both are empty until you set them, and release-please uses `GITHUB_TOKEN`. To set it up:

1. Create a GitHub App (**Settings → Developer settings → GitHub Apps → New GitHub App**) with no webhook and two repository permissions: **Contents: Read and write** and **Pull requests: Read and write**.
2. Install it on the repository, and generate a private key for it.
3. In the repository's **Settings → Secrets and variables → Actions**, add the app's client ID as the variable `RELEASE_APP_CLIENT_ID` and the private key as the secret `RELEASE_APP_PRIVATE_KEY`.

```yaml
  version:
    uses: apollogeddon/forgego/.github/workflows/version.yml@main
    with:
      app_client_id: ${{ vars.RELEASE_APP_CLIENT_ID }}
    secrets:
      APP_PRIVATE_KEY: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}
```

## Required permissions

Each root job grants what its pipeline's stages need, and nothing else:

| Root job | Permissions | Needed for |
| :--- | :--- | :--- |
| `library`, `service`, `website` | `contents: read`, `pull-requests: write` | Gitleaks reads a pull request's commits and comments on one it finds a secret in |
| `docker` | `contents: read`, `packages: write` | Pushing to GHCR |
| `version` | `contents: write`, `pull-requests: write` | release-please's tags, releases and release pull requests |
| `publish` | `contents: read`; `contents: write` for `assets`; `id-token: write` and `attestations: write` for `attest` | The proxy fetch; attaching the release's files and publishing the draft; their build provenance |
| `pages` | `pages: write`, `id-token: write` | GitHub Pages |
| `patch` | `contents: write`, `pull-requests: write` | Pushing the refreshed files to the `forgego/sync` branch, and the pull request for them |
| `merge` | `contents: write`, `pull-requests: write` | The review request, the merge and the dispatch |

GitHub checks a called workflow's permissions against the caller's before running anything, even a job that would be skipped. So a caller grants the union of what a pipeline's stages ask for. In `publish.yml`, `package` and the native builds ask for exactly `contents: read`, and `assets` asks for nothing and takes the caller's grant, so only a caller that turns `assets` on, a service's, grants `contents: write`. `attest` takes the caller's grant too, so only a caller that turns it on grants `id-token: write` and `attestations: write`.

## GitHub Free

Everything works in a private repository on GitHub Free. Two things GitHub offers there only to public repositories switch on by themselves once the repository is public, as each job checks `github.event.repository.private == false`:

- **Artifact attestations**: a service's `publish` job passes `attest`, so the release's files get a build provenance attestation, checked with `gh attestation verify`.
- **GitHub Pages**: a website's `pages` job deploys only from a public repository. On a paid plan, which serves Pages from a private repository too, drop that check from the job's `if`.
- **Dependency review**: the `scan` stage reviews a pull request's dependency changes with GitHub's advisories, which a private repository needs GitHub Code Security for.

A scheduled run has no `repository.private`, and the check reads that as private, which always works.

On a public repository, also turn on, in **Settings → Code security**:

- **CodeQL analysis**, with the default setup, for Go and GitHub Actions: it finds security bugs in the code and the workflows.
- **Secret scanning** and its **push protection**, which blocks a push that contains a known kind of secret.

A private repository on GitHub Free has neither; there Gitleaks, in the `scan` stage, catches committed secrets, and OSV-Scanner and govulncheck known vulnerabilities.

## Vulnerable dependencies

The `scan` stage fails a pull request that adds a known high or critical vulnerability, but nothing upgrades a module that becomes vulnerable later. Turn on **Settings → Code security → Dependabot security updates**, free in private repositories too: Dependabot then opens a pull request for each one, which the checks and `merge` handle like its other updates. `patch` no longer upgrades them on `main`.

For `patch`'s pull requests, and release-please's, turn on **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests**.

For GitHub Pages, set **Settings → Pages → Source** to **GitHub Actions**. For Dependabot auto-merge, turn on **Settings → General → Allow auto-merge**. Auto-merge squash-merges, so release-please lists each update once: a merge commit repeats the pull request's title, and release-please reads that as a second change. Merge your own pull requests the same way, with **Squash and merge**. Dependabot's GitHub Actions updates are never auto-merged: they change workflow files, which the workflow's `GITHUB_TOKEN` can't merge, so merge those pull requests yourself.
